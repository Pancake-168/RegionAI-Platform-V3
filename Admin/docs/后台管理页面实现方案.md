## 一、前置分析

### 1.1 SDK 版本对照

| 项目           | 原 Electron 版                                                                                                                                      | 新 Tauri 版                                                                               |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| SDK 包         | `@nocobase/client` **2.0.0-beta.1**（源码中 `import { APIClient } from '@nocobase/sdk'`，`@nocobase/sdk` 作为 `@nocobase/client` 的传递依赖被安装） | `@nocobase/sdk` **2.1.5**（当前为 `@nocobase/client@2.1.5` 的传递依赖，需提升为直接依赖） |
| APIClient 来源 | `import { APIClient } from '@nocobase/sdk'`                                                                                                         | `import { APIClient } from '@nocobase/sdk'`（**完全相同**）                               |
| auth 方法      | `client.auth.setToken()` / `client.auth.signIn()` / `client.auth.getToken()`                                                                        | **完全相同**                                                                              |
| resource       | `client.resource(name).list()`                                                                                                                      | **完全相同**                                                                              |
| request        | `client.request({ url, params, headers })`                                                                                                          | **完全相同**                                                                              |

#### 为什么不能用 `@nocobase/client` 的 APIClient

`@nocobase/client` 已经安装在项目中（v2.1.5），但其 `APIClient` **不能**在此场景使用。类型定义文件 `es/api-client/APIClient.d.ts` 揭示了原因：

```typescript
export declare class APIClient extends APIClientSDK {
  services: Record<string, Result<any, any>> // 依赖 ahooks Result 类型
  silence: boolean
  app: Application // 依赖完整 NocoBase Application 实例
  get notification(): NotificationInstance // 依赖 antd NotificationInstance
  interceptors(): void // 重写父类，可能访问 this.app
  // ...
}
```

`@nocobase/client` 的 APIClient 不仅是一个 HTTP 客户端——它绑定了：

- **antd** 的 `NotificationInstance`（通知系统）
- **ahooks** 的 `Result` 类型（service 状态管理）
- **NocoBase Application** 实例（`this.app`）

在新 Tauri 项目中，没有 NocoBase Application 上下文、没有 antd、没有 ahooks。直接使用 `@nocobase/client` 的 APIClient 会导致构造函数或拦截器在访问 `this.app` 时抛出运行时错误。

#### 正确方案：使用 `@nocobase/sdk`

`@nocobase/sdk@2.1.5` 已作为 `@nocobase/client` 的传递依赖安装在 `node_modules/@nocobase/sdk` 中。其 `APIClient` 是纯粹的 HTTP 客户端：

```typescript
// @nocobase/sdk/lib/APIClient.d.ts
export declare class APIClient {
  axios: AxiosInstance
  auth: Auth
  storage: BaseStorage
  request<T>(config): Promise<AxiosResponse<T>>
  resource(name, of?, headers?, cancel?): IResource
}
```

**依赖项仅有 `axios` + `qs`**，无 antd、无 ahooks、无 Application。API 签名与原 Electron 版使用的 `@nocobase/sdk` 完全一致，服务层代码可以 import 路径不变地直接迁移。

#### 实施操作

1. 在 `package.json` 中将 `@nocobase/sdk` 从传递依赖提升为**显式直接依赖**：
   ```json
   "@nocobase/sdk": "2.1.5"
   ```
2. 可选：从 `package.json` 中移除 `@nocobase/client`（当前未使用且携带大量 React/antd 依赖）

## 三、服务层迁移方案

### 3.0 日志规范（全局约束）

项目中已有统一的日志体系（`src/utils/logger.ts` → `createLogger`）。**服务层和 UI 层的每一个函数都必须接入此日志体系**，方便调试和测试。

#### 基本用法

```typescript
import { createLogger } from '@/utils/logger'

// 按函数粒度创建 logger：第一个参数是文件名，第二个是函数名
const log = createLogger('client.ts', 'createClient')

// 三种日志级别（禁用 debug）
log.info('关键操作成功', { id }) // 正常业务流程
log.warn('异常但可恢复', reason) // 降级、重试
log.error('错误', error) // 需要关注的故障
```

> `createLogger` 的前两个参数会写入日志前缀 `[RegionAI:文件名:函数名]`，在 Tauri 桌面端通过 IPC 桥接到 Rust 后端写入文件（开发模式 `%TEMP%/regionaiv3/logs/`，生产模式安装目录 `data/logs/`）。`registerTauriTransport()` 已在 `main.ts` 中调用，服务层文件无需重复初始化。

#### 日志粒度约定

| 位置                 | 日志策略                                                             |
| -------------------- | -------------------------------------------------------------------- |
| **每个 export 函数** | 入口处创建自己的 `const log = createLogger('文件名', '函数名')`      |
| API 请求发起时       | `log.info('开始请求', { url, params })`                              |
| API 请求成功时       | `log.info('请求成功', { status, count })`                            |
| API 请求失败时       | `log.warn('请求失败', { url, error: err.message })`                  |
| 缓存命中时           | `log.info('缓存命中', { key })`                                      |
| 认证相关操作         | `log.info('登录成功')` / `log.warn('登录失败', reason)`              |
| 客户端状态变更       | `log.info('客户端已创建', { baseURL })` / `log.info('客户端已清理')` |
| 分页循环中           | `log.info('分页获取', { page, count })`                              |

#### 禁止事项

- **禁止裸 `console.log`** — 所有日志必须走 `createLogger`
- **禁止在日志中输出完整 token** — token 仅输出前 8 位 + `...`（如 `eyJhbGci...`）
- **禁止在日志中输出完整密码** — 密码字段统一替换为 `***`
- **禁止使用 `log.debug`** — 不要用 debug 等级，仅使用 `log.info`、`log.warn`、`log.error`

**变更后的 `ensureNocoBaseAdminClient()` 逻辑**：

```typescript
async function createAdminClient(): Promise<APIClient | null> {
  const authStore = useNocoBaseAuthStore()
  if (!authStore.isLoggedIn) return null

  const baseURL = resolveAdminBaseURL()
  return await loginByToken(baseURL, authStore.token!)
}

export async function ensureNocoBaseAdminClient(): Promise<APIClient | null> {
  // 已有客户端直接复用
  const existingClient = nocoBaseService.peekAuthedClient()
  if (existingClient) return existingClient

  // 去重：同一时刻只有一个登录 Promise
  if (!adminClientPromise) {
    adminClientPromise = createAdminClient().finally(() => {
      adminClientPromise = null
    })
  }
  return await adminClientPromise
}
```

若 store 中无 token（用户尚未登录），返回 null，由 UI 层展示"请先登录"空状态。

### 4.2 设计规范遵循

严格遵循 `docs/新页面编写规范.md` 的三层架构：

**样式策略**：
- 页面结构布局：`:style` 绑定 `var(--xxx)` Token（配合 `as const` 常量）
- 面板/卡片子组件：`*.module.css`
- 颜色/圆角/阴影：全部引用 CSS 变量，绝不死写

**组件复用**：
- 列表项使用全局 `.btn.subtle` 类
- 数据表格使用 `var(--text)`、`var(--muted)`、`var(--glass-brd)` 等 Token
- 无数据时使用 `EmptyState` 组件

**缓存使用模式**（以子应用切换为例）：

```typescript
watch(
  () => props.selectedApp,
  async (app) => {
    if (!app?.name) return
    // 1. 先查缓存
    const cached = appInfoCache.get(app.name)
    if (cached) {
      appInfo.value = cached
      return
    }
    // 2. 再查 inFlight（去重）
    if (appInfoInFlight.has(app.name)) {
      appInfo.value = await appInfoInFlight.get(app.name)!
      return
    }
    // 3. 缓存和 inFlight 均未命中 → 发起请求
    appLoading.value = true
    const task = getAllAvailableNocoBaseInfoByApplication(app.name)
    appInfoInFlight.set(app.name, task)
    const result = await task
    appInfoInFlight.delete(app.name)
    appLoading.value = false
    if (result) appInfoCache.set(app.name, result)
    appInfo.value = result
  },
  { immediate: true },
)
```

同样的缓存/去重模式应用于 table（key 为 `${appName}:${collection}`）和 SSO（key 为 appName）。

#### 5.2.2 为什么不需要 `nocobase-traffic-fix` 插件

原 Electron 项目中，`nocobase-traffic-fix.ts` 插件存在的原因及新版不需要的原因分析：

**原版插件的职责**：

```
Vite dev server 中间件
  │
  ├─ 排除 Vite 内部请求（__x00__、/@、/node_modules/）
  ├─ 识别 NocoBase 请求：
  │   ├─ URL 含 noco=1
  │   ├─ Referer 含 noco=1 或 /nocobase-proxy
  │   ├─ URL 含 :  （SDK resource:action 格式）
  │   └─ URL 含 umi.js / .async.js / vendors-node_modules
  ├─ 已带 /nocobase-proxy 前缀 → 跳过
  └─ 未带前缀 → 重写为 /nocobase-proxy + url
```

**原版为什么需要它**：原 Electron 项目不仅在管理页面中通过 SDK 调用 API，还通过 **iframe 嵌入完整的 NocoBase 管理后台页面**。iframe 内加载的是 NocoBase 自身的 React 前端（umi.js、vendors-node_modules 等），这些请求的 URL 不经过 APIClient 的 baseURL 拼接，因此不天然带 `/nocobase-proxy` 前缀。插件通过检查 Referer 头和 URL 特征（`umi.js`、`.async.js`）来识别并补全前缀。

**新版为什么不需要**：新版 Tauri 项目**不嵌入 NocoBase iframe 页面**，所有 NocoBase 交互均通过 `@nocobase/sdk` 的 APIClient 以 API 调用方式完成。APIClient 的 `baseURL` 设置为 `/nocobase-proxy/api`，因此 SDK 发出的**每一个请求**都天然带 `/nocobase-proxy` 前缀，直接匹配 Vite proxy 的 `/nocobase-proxy` 规则，无需中间件层额外识别和重写。

**结论**：两条 `/nocobase-proxy` + `/api` 的标准 Vite proxy 规则已完整覆盖新版的需求。

#### 5.2.3 CSP 与 Tauri 安全策略

Tauri 2 中，`tauri.conf.json` 的 `security.csp` 设为 `null` 时，WebView **不启用任何 CSP**，允许向任意域名发起 HTTP 请求。这与 Electron 中不设 CSP 的行为一致。

当前 `tauri.conf.json` 中 `"csp": null`，已满足局域网私有部署的 HTTP 直连需求。

**不需要修改的项**：

| 配置项                      | 当前值                                                                             | 结论                                                                       |
| --------------------------- | ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `security.csp`              | `null`                                                                             | 不限制，与 Electron 一致                                                   |
| `capabilities/default.json` | 含 `core:default`、`opener:default`、`dialog:default`、`fs:default` 及窗口控制权限 | 不涉及网络请求权限（网络由 Chromium 内核直发，不走 Tauri capability 体系） |
| `lib.rs` WebviewUrl         | Dev: `http://localhost:1420`，Prod: `index.html`                                   | 与 Electron 的 `app://` 加载本地文件等效                                   |
| `lib.rs` 窗口创建           | `decorations(false)`、`inner_size(1000,600)`、`min_inner_size(800,500)`            | 不涉及网络                                                                 |
| `index.html`                | 标准 HTML5，无 `<meta http-equiv="Content-Security-Policy">`                       | 无额外限制                                                                 |

#### 5.2.4 局域网部署的 allowedHosts 分析

**问题**：局域网私有部署场景下，开发环境可能需要从其他机器访问 Vite dev server（例如调试移动端或同事联调）。Vite 的 `server.allowedHosts` 控制哪些 Host 头的请求被接受。

**当前状态**：Tauri 版的 `vite.config.ts` 中**未配置** `allowedHosts`。Vite 默认行为是允许所有 Host（等价于 `allowedHosts: true`），仅当显式配置为数组时才做白名单校验。

**局域网场景分析**：

| 场景                                            | 访问方式                                                   | `allowedHosts` 是否需要配置                                |
| ----------------------------------------------- | ---------------------------------------------------------- | ---------------------------------------------------------- |
| 本机开发（`localhost:1420`）                    | `npm run tauri dev` → Tauri 自动启动 dev server + 打开窗口 | 不需要 — Tauri 通过 `devUrl: "http://localhost:1420"` 加载 |
| 局域网其他设备访问（`http://192.168.x.x:1420`） | 浏览器直接访问                                             | 不需要 — Vite 默认允许所有 Host                            |
| 通过局域网 IP 的 Tauri 窗口（`TAURI_DEV_HOST`） | 设置 `TAURI_DEV_HOST=192.168.x.x`                          | 不需要 — `host` 配置已处理绑定地址，allowedHosts 默认放行  |
| 生产环境（Tauri 打包后）                        | WebView 加载本地 `index.html`                              | 不适用 — 无 Vite dev server，无 allowedHosts 概念          |

**结论**：当前不配置 `allowedHosts` 是安全的，Vite 默认行为已满足局域网开发需求。原 Electron 版配置 `allowedHosts` 是因为设置了具体的域名白名单做访问控制——这是在公网可解析域名场景下的安全加固，而 Tauri 版是纯局域网/本机场景，无此需求。若后续部署到公网可解析域名，届时再添加白名单。

#### 5.2.5 与 Electron 版的权限等价性

| 场景               | Electron 版                                              | Tauri 版                                      | 等价                         |
| ------------------ | -------------------------------------------------------- | --------------------------------------------- | ---------------------------- |
| Dev 环境 HTTP 代理 | Vite proxy + `nocobase-traffic-fix` 插件                 | Vite proxy（纯 SDK API 调用，无 iframe 嵌入） | 是（覆盖范围更窄但满足需求） |
| 打包后 HTTP 直连   | `app://` 协议 + `fetch` 直连（检测协议后切换到绝对 URL） | Tauri WebView + `fetch` 直连                  | 是                           |
| WebSocket 代理     | `/ws` 和 `/socket.io` 按 referer 代理                    | 同上，Vite proxy `ws: true`                   | 是                           |
| 无 CSP 限制        | Electron 默认无 CSP                                      | `csp: null`                                   | 是                           |
| 局域网域名         | Vite `allowedHosts` 白名单                               | Vite 默认全部允许                             | 满足（局域网场景无需白名单） |

## 六、与登录流程的对接约定

后台管理页面**不负责登录**，只依赖 `NocoBaseAuth` store。约定如下：

1. **登录由独立登录页面完成**（后续实现），登录页负责：
   - 获取用户 token（Token 登录或账号密码登录）
   - 确定服务器地址
   - 调用 `nocoBaseAuthStore.setAuth(token, baseURL)`
   - 调用 `nocoBaseService.createClient(token, baseURL)`

2. **后台管理页**进入时：
   - 检查 `nocoBaseAuthStore.isLoggedIn`
   - 若已登录，自动调用 `getAllAvailableNocoBaseInfo()` 获取数据
   - 若未登录，展示空状态提示"请先登录"

3. **token 传递**：通过 Pinia store 共享，不在组件间 props 传递，不存 URL 参数
