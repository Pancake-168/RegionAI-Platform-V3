# v3 竞态分析与启动策略

> 基于 YanJing-Matrix-Platform（v1）和 RegionAI-Platform2（v2）的 Matrix 服务层实践得出的结论。

---

## 提问1：选用matrix作为底层通信，综合了这两个项目来看，matrix核心数据库该用什么？

**推荐：IndexedDB（matrix-js-sdk 原生 IndexedDBStore），但必须采用项目2的延迟启动策略。**

理由：

1. **两个项目一致选择 IndexedDB** — 说明在这个架构下 IndexedDB 是经过验证的可行方案。`indexeddbStore.ts` 在 v1 和 v2 中逻辑完全相同，无需重复造轮子。

2. **项目2修复了关键竞态问题** — v1 在 `useAccessTokenLogin` 中立即调 `startClient()`，SDK 首轮 `/sync` 与 IndexedDB 本地数据读取存在竞争。v2 将 `/sync` 抽离为 `startSyncIfNeeded()`，由 `projectStart.ts` 在本地数据恢复完成后调用。v3 直接继承这个模式即可，不需要换数据库。

3. **不推荐换 SQLite 或其他方案** — matrix-js-sdk 只提供了 `IStore` 接口，官方实现只有 `IndexedDBStore` 和 `MemoryStore`。自己实现一个 SQLite 适配的 `IStore` 工作量大，且 `/sync` 返回的 JSON 数据量大、结构嵌套深，在 SQLite 里做序列化/反序列化没有性能优势。

4. **MemoryStore 不可取** — 刷新页面即丢失全部同步数据，每次都要全量 `/sync`，服务端压力和启动时间都会成倍增加。

**结论：沿用 IndexedDBStore + 延迟 startClient 策略。** v3 只需要把 v2 的 `indexeddbStore.ts` 和 `startSyncIfNeeded` 模式搬过去即可。

---

## 提问2：关键竞态指的是？

在 v1 的 `useAccessTokenLogin` 中，流程是这样的（简化）：

```
1. IndexedDBStore.startup()        // 打开数据库
2. 保存登录配置参数（setMatrixLoginConfigRaw / setMatrixLoginConfig）
3. client.startClient()            // 立刻发起首次 /sync
4. 绑定 eventManager、timelineService

（注：v1 是先 startClient 后绑定的，但由于 /sync 是 HTTP 异步请求，响应返回时 bind 早已执行完毕，因此这个先后顺序不影响竞态——竞态的核心不在绑定时机，而在 /sync 发起的时机相对于 projectStart 数据恢复的早晚。）
```

首次 `/sync` 是**全量同步**，服务端会把你所有房间的状态、成员列表、最近的 timeline 事件一次性推下来。这些数据到达后立即触发：

- `eventManager` 派发 `SYNC_COMPLETED`、`MESSAGE_RECEIVED` 等事件
- `timelineService` 收到事件后写入 `timelineStore`
- UI 层的 `watch`/`computed` 响应式更新开始渲染房间列表

但此时，下列应用层本地数据**可能还没恢复完**：

- `specialRoomStore`（哪些房间是 AIAdmin/AISupport 系统房间）
- `ClassDisplayCache`（房间分类结果缓存）
- `SystemStorage` 中的用户配置
- 登录配置参数

这就产生了一个竞态：**SDK 的数据已经就绪并触发渲染了，但应用层自己的配置和缓存还没读完。** 结果是房间列表可能短暂按错误分类展示（比如 AIAdmin 被当成普通房间），然后再被后续恢复覆盖，产生视觉闪烁或短暂的错误状态。

v2 的解决方案：把 `startClient()` 从 `useAccessTokenLogin` 中**剥离**成独立的 `startSyncIfNeeded()`，延迟到 `projectStart.ts` 中本地数据恢复全部完成后才调用：

```
1. IndexedDBStore.startup()        // 打开数据库
2. 绑定 eventManager、timelineService（只注册监听，不发 /sync）
3. ← 返回，让 projectStart 继续恢复本地数据...
4. specialRoomStore.ensureLoaded()  // 系统房间列表恢复完成
5. ClassDisplayCache 读取完成
6. SystemStorage 恢复完成
7. matrixClient.startSyncIfNeeded() // ← 此时才发起首次 /sync
```

相当于**人为将 `/sync` 的起点推迟到本地数据恢复的终点之后**，保证 SDK 的第一批事件到达时，所有应用层依赖项已经就绪。

这其中包含 Matrix 系统级别的启动和人为房间分类的读取吗？

**Matrix 系统级别的启动不包含在竞态中。**

v1 已经正确处理了 IndexedDBStore 的启动时序 —— `startup()` 是 `await` 的，完成后才到 `startClient()`。这块 v1 和 v2 没有区别，不是竞态的构成部分。

```
// v1 和 v2 都正确 await 了这一步
await maybeStartup.startup()     // ← 已等待完成
this.AuthenticatedMatrixClient.startClient()  // ← /sync 发起
```

**真正的竞态是：**

- v1 的 `/sync` 在 `useAccessTokenLogin` 内部就发出了，此时**函数调用栈还在登录流程里**
- `/sync` 返回的数据立即可用，而 `specialRoomStore` 和用户配置等数据要到 `projectStart` 阶段才去读
- 这个时序差就是竞态窗口

**房间分类的读取**是这个竞态的一部分，但不是全部。具体来说：

v1 中没有 classification 体系，但有一个等价物 —— `specialRoomStore.ensureLoaded()`。系统房间列表（哪些是 AIAdmin、哪些是 AISupport）需要在 `/sync` 之前就位，否则房间事件到达时无法正确判定系统房间身份。

v2 新增了完整的 classification 体系后，竞态参与方变多了：`ClassDisplayCache`、`UserConfig`、`specialRoomStore` 都需要在 `/sync` 首轮事件触发前就绪。这就是 v2 把 `startClient` 延迟到 `projectStart` 末尾的原因 —— 把所有本地数据恢复全部收敛到 `/sync` 启动之前。

## 提问3：原本位于前端的房间分类逻辑，现在不需要了，因为后端提供了。那么此时不管是v1还是v2都不再需要走房间分类，v3可以直接调后端api拿分类后的结果。此时竞态问题还存在吗？

这个竞态会因为"分类移到后端"而缩小范围，但**不会完全消失**。

**消失的部分 —— 分类竞态**

原本的竞态链条中，`specialRoomStore.ensureLoaded()` 和 `ClassDisplayCache` 读取完成是 `/sync` 启动的前置条件，因为这些数据决定了"这个 roomId 是 AIAdmin 还是普通房间"。v2 把 `startClient` 推迟到这些完成之后，就是为了等分类数据就位。

现在分类直接调后端 API 拿结果，前端不再本地运行 classifier，那么：

- `ClassDisplayCache` 可以删除
- `specialRoomStore` 中用于分类判定的那部分不再关键
- 分类阶段的本地数据依赖消失了

**仍然存在的部分 —— session/配置 竞态**

但 `/sync` 的首轮事件仍然会触发 timeline store、eventManager。以下数据仍然必须在 `/sync` 启动前就位，否则依然有问题：

- 当前激活用户的 username（按用户隔离的存储读取）
- `SystemStorage` 中的用户配置（登录参数、server URL 等）
- 如果需要根据用户配置决定某些房间的显示/隐藏，这些配置也必须先读

这些与"房间分类"无关，但仍然是 `/sync` 启动的前置依赖。

**v3 的 projectStart 推荐顺序**：

```
1. SystemStorage 恢复激活用户信息
2. 调后端分类 API 拿房间列表（替代本地 classifier）
3. 其他用户配置恢复
4. matrixClient.startSyncIfNeeded()  ← 所有依赖就绪后才启动
```

**注意：上述保守结论在提问4的补充前提下会被推翻，见下文。**

## 提问4：v3的逻辑，我说过了分类由后端进行，后端api能提供全部分类结果，因此，项目内不会再有直接拿sdk的rooms去渲染UI列表的情况，而是后端返回的room列表

**竞态问题在 v3 中彻底消失。**

Q3 中保守保留了 session/配置竞态，前提是"UI 渲染房间列表时仍走 SDK rooms"。但 Q4 补充了一个关键前提：**UI 渲染的 room 列表来源从 SDK 切换到了后端 API**。这意味着：

- Q3 担心的 session/配置竞态，其下游消费者是 room 列表渲染（分类判定、显示/隐藏决策）。当 room 列表完全由后端 API 提供时，这些配置数据不再被 `/sync` 事件处理器消费。
- `/sync` 事件处理器（timelineStore 写入、eventManager 派发）本身不依赖 username、SystemStorage 配置 —— 它们只存储和转发原始 Matrix 事件，不需要任何业务配置就能正常工作。
- 唯一仍然依赖配置数据的模块是 message 发送（需要 username + token），但 token 在 `useAccessTokenLogin` 阶段就已经写入存储，远早于 `/sync` 启动。

因此 Q3 和 Q4 的结论并不矛盾，而是**前提递进导致结论更新**：

```
Q3 前提：UI 列表来自 SDK rooms（/sync）
  → session/配置数据可能被列表渲染消费 → 保留延迟启动

Q4 前提：UI 列表来自后端 API，不再用 SDK rooms 渲染
  → session/配置数据不再被任何 /sync 事件处理器消费 → 延迟启动不必要
```

```
v1/v2 的 UI 渲染链：
  startClient() → /sync 返回 rooms → eventManager 派发 → timelineStore
      → UI 用 SDK rooms 渲染列表 → 依赖分类数据就绪 → 竞态

v3 的 UI 渲染链：
  后端 API 返回 room 列表 → UI 渲染 ← 与 /sync 完全解耦
  startClient() → /sync 返回 rooms → eventManager 派发 → timelineStore
      → 仅用于消息收发，不影响列表渲染
```

两条链互不阻塞。`/sync` 可以任何时候启动，UI 不会因为它先到或晚到而出错。

**这意味着 v3 不需要 `startSyncIfNeeded` 模式。** 反而应该让 `/sync` 尽早启动 —— 登录完成就发，和调后端 API 并行，等 API 返回 room 列表时，`/sync` 大概率已经跑完首轮，timeline 数据已在 store 中就绪，打开任意房间消息都是即时可用的。

## v3 还需要清理的模块

### incrementalClassify —— 必须移除

v2 的 `incrementalClassify.ts` 监听 `ROOM_JOINED` / `ROOM_INVITED` / `ROOM_UPDATED` 并在事件后调用 `classifyRooms()` 触发本地分类器重算。v3 分类移到后端后：

- `classifyRooms` 不可用（它依赖 `classification/classifier.ts`）
- 增量分类逻辑本身不再需要 —— 房间分类由后端维护，前端只需调 API 刷新列表

**处理方式：直接删除 `incrementalClassify.ts` 及其调用点（`startIncrementalClassify` / `markFirstClassificationDone` / `stopIncrementalClassify`）。** 如果需要在房间成员变更后刷新后端 API 返回的列表，应该改为一个简单的"调后端 API 重新拉列表"的函数，而不是走本地 classifier。
