# v3 代码层面改动规划

> 基于 v1（YanJing-Matrix-Platform）和 v2（RegionAI-Platform2）的服务层分析，规划 v3 需要做出的具体代码改动。

---

## 前提

两个关键事实（由用户确认）：

1. **v1 已经使用后端 API 提供房间列表**。`NewRoomStore` 通过 `New_RoomList` / `New_GetDMRooms` / `New_ListAgentSessions` 三个后端接口获取"要展示哪些房间"，UI 组件 `NewRoomList` 从 `newRoomStore.dmRooms` / `newRoomStore.groupRooms` / `newRoomStore.botSessions` 读取房间身份列表。Matrix SDK 只用于补充展示属性（通过 `c.getRoom(room_id)` 获取 `Room` 对象，再取 name、avatar、preview、unread、time）。

2. **头像等内容依旧取自 Matrix 系统**。DM 头像通过 `avatarHelper.resolveAvatarUrl(matrixId)` 走 Matrix profile 解析，展示名通过 `c.getUser(id).displayName` 获取，时间/预览/未读数通过 `MatrixClientRoom` 的方法从 SDK Room 对象读取。`/sync` 必须跑完首轮，这些 Room 对象才有数据。

## 一、删除项

### 1.1 本地房间分类系统（整个目录删除）

```
删除：src/services/Matrix/classification/  （整个目录）
  - classifier.ts           (~690行)
  - displayResolver.ts      (~170行)
  - memberTypeResolver.ts   (~130行)
  - systemRoomRules.ts      (~120行)
```

**原因**：v3 分类由后端 API 完成，前端不再本地运行分类算法。

### 1.2 增量分类

```
删除：src/services/Matrix/incrementalClassify.ts  (~135行)
```

**原因**：依赖 `classifyRooms()`，分类移除后不再可用。

**清理调用点**：在 `projectStart.ts` 中移除对 `startIncrementalClassify()` / `markFirstClassificationDone()` / `stopIncrementalClassify()` 的调用。在 store 中移除对 `refreshFromClassification()` 的依赖。

### 1.3 ClassDisplayCache

```
删除：SystemStorageManager 中以下方法的定义和所有调用点
  - getClassDisplayCache()
  - setClassDisplayCache()
```

**原因**：分类结果缓存不再需要，房间分类由后端维护。

### 1.4 Space 空间反查

```
删除：src/services/Matrix/space.ts  (~480行)
```

**原因**：v2 和 v3 均不使用 Matrix Space 功能。如果 v3 需要空间功能，由后端 API 提供。

### 1.5 refreshRoomState.ts

```
删除：src/services/Matrix/refreshRoomState.ts  (~240行)
删除：src/utils/roomPeerInfo.ts（如仅被 refreshRoomState 使用）
```

**原因**：该文件的核心职责是"刷新房间列表 + 分类 + 选择当前房间"。v3 中房间列表由 `NewRoomStore` 的后端 API 刷新，分类由后端完成，房间选择逻辑应下沉到 UI 组件或 store 中。

**替代**：在 `NewRoomStore` 或 UI 层实现一个轻量级的房间选择函数（优先 preferredRoomId → 当前 roomId → 第一个 joined 房间），不再需要原文件中的分类、遮罩、预拉取等逻辑。

### 1.6 MSGOperations/MsgForward.ts 中的逐条转发

```
删除：forwardMessageIndividual() 函数（仅 v1 有，v2 已移除）
```

**原因**：v2 已移除此功能，v3 保持一致。

### 1.7 serverNotice.ts

```
删除：src/services/Matrix/serverNotice.ts  (~300行)
```

**原因**：这是 v2 中用于调试 Synapse `server_notices` 配置的诊断工具（检测 `m.server_notice` 标签并 dump 房间信息）。与房间分类无关，属于开发期诊断工具。v3 服务器若未启用 `server_notices` 则无保留必要。如后续需要服务端通知功能，应由后端 API 统一提供通知列表，而非前端遍历 Matrix 房间标签。

## 三、需要以 v2 为基准改造的模块

### 3.1 client.ts

**以 v2 为基础，做以下调整**：

| 改动 | 说明 |
|------|------|
| **保留** v2 的多账号体系 | `getActiveUsername()`、所有存储操作传 `username` 参数 |
| **保留** v2 的日志系统 | `logInfo`/`logWarn`/`logError` 替代 `console` |
| **保留** v2 的 `startSyncIfNeeded()` 方法 | 但**调用策略改变**：不再延迟到 projectStart 末尾，而是在 `useAccessTokenLogin` 完成后**立即调用**，与后端 API 并行 |
| **保留** v2 的 `options.verifiedUserId` | whoami 复用优化 |
| **删除** v2 的 startupTiming | 性能打点按需保留，非必须 |
| **保留** v2 的 `knockRoom` | |

**v3 的 startClient 调用策略**：

```
v1：useAccessTokenLogin 内 startClient → /sync 与 projectStart 竞态
v2：useAccessTokenLogin 不 start → projectStart 末尾 startSyncIfNeeded → 延迟启动
v3：useAccessTokenLogin 完成后立即 startClient → /sync 与后端 API 并行
```

v3 不需要延迟的理由：后端 API 提供房间身份列表，`/sync` 提供 Room 对象的展示属性。UI 渲染时通过 `c.getRoom(room_id)` 取 Room，如果某个 room 的 `/sync` 还没到，`getRoom()` 返回 null，UI 跳过该项。两者互不阻塞，且 `/sync` 首轮通常远快于后端 API 调用，所以 API 返回时 Room 对象大概率已就绪。

### 3.2 room.ts

**以 v2 为基础，保留**：

| 改动 | 说明 |
|------|------|
| v2 的 `logWarn` 日志系统 | 全类已迁移 |
| v2 的 `getUnreadCount` | 使用 `sdkRoom.getUnreadNotificationCount()` 替代本地 store |
| v2 的 `getReadMarkerEventId` | 新增方法 |

**不需要额外改动**。`room.ts` 本身与分类逻辑无关，只提供通用 Room 属性读取。

### 3.3 message.ts

**以 v2 为基础，保留**：

| 改动 | 说明 |
|------|------|
| v2 的 HTML 格式发送 | `format` + `formatted_body` + `buildRichHtml` + `buildMentionHtml` |
| v2 的 `htmlBody` 选项 | `SendTextOptions` 和 `SendCompositeOptions` 都保留 |
| v2 的消息指纹缓存 | `messageFingerprints` |

**需要决策的项**：

| 项 | 说明 |
|------|------|
| `turnId` 字段 | v2 删除了，v3 是否需要取决于后端是否用其他方式关联对话轮次。如不需要，保持删除 |

### 3.4 roomManagement.ts

**以 v2 为基础**，无额外改动。逻辑与 v1 完全一致，仅日志迁移。

### 3.5 search.ts

**以 v2 为基础**，无额外改动。逻辑与 v1 完全一致，仅日志迁移。

### 3.6 eventManager.ts

**以 v2 为基础**。需要注意 `tryParseExtensible` 中 `[event, error]` 数组包裹的参数结构，确保 v3 的 `logWarn` 实现能正确处理数组参数的序列化。

## 四、v3 的 projectStart 启动顺序

```
1. IndexedDBStore.startup()           // 打开数据库
2. 绑定 eventManager、timelineService // 注册监听
3. matrixClient.startSyncIfNeeded()   // 立即发起 /sync（不等待）
4. SystemStorage 恢复激活用户信息     // 并行
5. NewRoomStore 刷新房间列表（后端API）// 并行
6. UI 渲染房间列表                    // 此时 /sync 大概率已完成首轮
```

`/sync` 在步骤 3 就启动，步骤 4、5 与它并行。UI 在步骤 6 渲染时，对每个 room_id 调 `c.getRoom(room_id)` 取展示属性。未同步到的 room 暂时不出现在列表中，等 `/sync` 到达后通过响应式更新自动补上。
